## 1. الغرض

هذه الجولة لا تسأل «كيف نصلح؟»، بل «من يملك الحقيقة؟»:

1. تعريف build الصحيح.
2. تعريف atom roots.
3. اكتشاف execution targets.
4. حدود معرفة Core.
5. تعريف Boot Success.
6. تعريف Release Success.

القاعدة الحاكمة:

```text
لا يجوز إصلاح عرض قبل تعيين مصدر الحقيقة الذي يحكمه.
```

### 2.3 الحكم

```text

الحالة: مثبت.
```

### 2.4 من يملك العقد حاليًا؟

لا يوجد مالك منفرد نافذ. `unified_release.json` هو أحدث إعلان، لكنه لا يفرض نفسه على بوابات 212، ولا على `PACKAGE_BUILD.txt`، ولا على معرفات البناء داخل الذرات.

إذن القرار لم يُحسم بعد:

```text
233/76 = أحدث إعلان إصدار
212     = مرجع قديم ما زال مستخدمًا في بوابات وملفات
```

لا يتم اختيار أحدهما في التدقيق، لأن الاختيار قرار إصدار/مالك وليس استنتاجًا تقنيًا.

## 3. العقد الثاني: مالك `atom roots`

### 3.1 مسار Core Boot الفعلي

```text
run_core.py:39-43
    QUANT_CORE_CONFIG
        ↓
core_config
        ↓
run_core.py:50
    atoms_root = PROJECT_ROOT / core_config.get("atoms_root", "atoms")
        ↓
run_core.py:89-92
    Bootloader(atoms_root, ...)
```

هذا هو مصدر المسار الذي يستخدمه Bootloader فعليًا.

### 3.2 المسار المستخدم في فحص execution

```text
run_core.py:360-363
    QUANT_ATOMS_ROOT أو PROJECT_ROOT/atoms
```

هذا مصدر ثانٍ مستقل عن `core_config.atoms_root`.

### 3.3 مسارات الإصدار

- `scripts/run_forex.py:12-13` يحدد `QUANT_CORE_CONFIG` و`QUANT_ATOMS_ROOT` للفوركس.
- `scripts/run_crypto.py:12-13` يحدد القيم الخاصة بالكريبتو.
- `scripts/verify_unified.py:17-18` يثبت الجذور إلى `ROOT/atoms` و`ROOT/atoms_crypto`.
- `governance/server.py:54` يختار `atoms` أو `atoms_crypto` حسب `QUANT_GOV_MARKET`.

### 3.4 الحكم

```text
Bootloader root owner        = core_config.atoms_root
Execution preflight owner    = QUANT_ATOMS_ROOT
Release verification owner   = hard-coded ROOT/atoms* paths
Governance server owner      = QUANT_GOV_MARKET
```

```text
F-CONTRACT-002
Atom Root Single Truth = غير موجود؛ توجد أربعة مصادر حدودية.
الحالة: مثبت بنيويًا.
```

لا يوجد دليل أن هذا سبب فشل Core مع صفر ذرات، لكنه خطر انجراف بين المسار الذي يقلع والمسار الذي يُفحص.

## 5. العقد الرابع: ماذا يجب أن تعرف Core؟

### 5.1 ما لم يظهر داخل Core التنفيذية

فحص imports في `core/` لم يثبت استيرادًا تنفيذيًا من:

```text
governance
transport
atoms
atoms_crypto
```

كما لم يثبت اسم أو رقم ذرة محددة داخل Bootloader أو Manifest Loader كشرط تنفيذ عام.

هذه نقطة إيجابية:

```text
Core → atom code direct import = غير مثبت
Core → governance/runner direct import = غير مثبت داخل core/
```

### 5.2 المعرفة النطاقية الموجودة

الموضع:

```text
core/api/app.py:255-267
```

يوجد allowlist صريح:

```python
"crypto.universe.override.command"
"crypto.universe.scan.requested"
```

ووصف API خاص بلوحة Crypto.

### 5.3 الحكم

```text
Core لا تبدو معتمدة على ذرة محددة عند Boot.
لكن core/api تحتوي معرفة نطاقية عن Crypto.
```

```text
F-CONTRACT-004
Core Domain Knowledge Boundary = خرق نطاقي مثبت داخل API.
```

هذا لا يساوي:

```text
Core depends on Crypto atoms
```

بل يساوي:

```text
Core API knows a Crypto domain event vocabulary
```

## 6. العقد الخامس: ما هو Boot Success؟

### 6.1 تعريف `Bootloader`

```text
core/bootloader.py:40-49
```

`BootReport` يحتوي:

```text
success
booted
failed
excluded
scan_failures
abort_reason
```

والقيمة تُبنى في:

```text
core/bootloader.py:154-160
```

على أساس عدم وجود `critical_failures`، لا على أساس عدد ذرات ثابت.

لذلك يمكن أن يكون:

```text
success=True
booted=[]
```

عند غياب الذرات، وهو متسق مع اختبار zero-atoms.

### 6.2 تعريف فحص الإقلاع

```text

```

لا يكتفي بوصول BootReport؛ بل يفرض:

```text
started == 212
failed == []
excluded == []
```

### 6.3 تعريف تشغيل الإصدار الموحّد

```text
scripts/launch_unified.py:117-129
```

يعتبر النجاح جاهزية المنافذ المطلوبة، ثم يرجع 0 إذا كانت كلها جاهزة.

### 6.4 الحكم

توجد ثلاثة معانٍ مختلفة لـBoot Success:

```text
Bootloader.success
    = لا critical failures

check_boot PASS
    = 212 ذرة بدأت، بلا فشل أو استبعاد

launch_unified PASS
    = المنافذ المطلوبة جاهزة
```

```text
F-CONTRACT-005
Boot Success Contract = متعدد وغير موحد.
الحالة: مثبت.
```

مهم: `Bootloader.success` و`Release readiness` ليسا الشيء نفسه.
