# 3. P0-3 — محسوم: الغلاف الحقيقي ستة حقول

`core/event_bus.py:276-281` — ما يحقنه الناقل فعلاً عند كل `publish`:

```python
base.setdefault("source",          publisher)          # نص المنتج
base.setdefault("event_id",        str(uuid.uuid4()))
base.setdefault("trace_id",        current_trace_id.get() or str(uuid.uuid4()))
base.setdefault("parent_event_id", current_event_id.get())
base.setdefault("parent_event",    current_event.get())
base.setdefault("timestamp",       self.now())         # float epoch مصحّح
```

## موجود ✅

`event_id` · `trace_id` · `parent_event_id` · `parent_event` · `source` · `timestamp`

## غير موجود ❌

| الحقل المقترح | الواقع |
|---|---|
| `event_name` | ليس حقلاً — وسيط دالّة منفصل |
| `event_version` | غير موجود إطلاقاً |
| `entity_type` / `entity_id` | غير موجود |
| `source_section` / `owner_section` | غير موجود (`source` نص حر) |
| `received_timestamp` | غير موجود |
| `sequence` | **غير موجود إطلاقاً** |
| `quality` | **غير موجود إطلاقاً** |
| `scope` | **غير موجود إطلاقاً** |
| `boot_id` | **غير موجود إطلاقاً** |

**9 من 15 حقلاً في الغلاف المقترح غير موجودة.**

## ثلاث نتائج مباشرة

**١. `timestamp` رقم عشري، لا نص.**
كل schemas المقترحة تكتب `"format": "date-time"`. عدم تطابق نوعي في **كل** حقل زمني. إما تحويل في طبقة الاستقبال أو تصحيح العقد.

**٢. `setdefault` يعني أن المنتج يستطيع تزوير كل شيء.**
ذرّة تمرّر `event_id` أو `timestamp` في حمولتها → الناقل يحترمها ولا يستبدلها. الهوية والوقت **ليسا مضمونين من الناقل**، هما افتراضيان فقط. هذا يهدم فرضية «القيمة قابلة للتتبع» في §6 من الدستور ما لم تتحقق الحوكمة منهما.

**٣. §45 و§42/43 غير قابلين للتنفيذ كما كُتبا.**
كشف فجوة التسلسل يحتاج `sequence`. التعافي بعد إعادة التشغيل يحتاج `boot_id`. لا وجود لأيّهما، وإضافتهما = تعديل النواة = مخالفة §3.2 من الدستور.

## القرار المطلوب — لا يمكن تأجيله

| الخيار | الكلفة |
|---|---|
| **أ** — إضافة الحقول للنواة | يخالف §3.2 صراحةً |
| **ب** — الحوكمة تصنعها | الحوكمة تصبح مُسقِطاً ذا حالة، لا واجهة قراءة |
| **ج** — إسقاطها من الغلاف | فقدان §43 و§45 نهائياً |

**التوصية: ب، بحدود صريحة.** الحوكمة تستطيع اشتقاق `received_timestamp` (بديهي) و`sequence` (عدّادها هي لكل اسم حدث) و`boot_id` (كشف بدء عملية النواة) و`quality` (نتيجة تحققها هي) — بلا لمس النواة.

**لكن يجب وسم هذه الحقول صراحةً كـ«حقائق ملاحَظة من الحوكمة» لا «حقائق من النواة».** تسلسل الحوكمة ليس ترتيب النواة، وخلطهما يعني أن اللوحة ستدّعي معرفة ترتيب لا تملكه.

# 4. أخطر اكتشاف — heuristic الإعادة يكسر السؤال الرئيسي

`core/event_bus.py:57-64` يقرر «هل هذا أمر؟» بـ**مطابقة نص جزئية**:

```python
_COMMAND_MARKERS = ("order", ".buy", ".sell", ".execute", ".cancel",
                    "final_decision", "command", ".submit", ".send")
def _is_command(name): return any(m in name for m in _COMMAND_MARKERS)
def _is_replayable(name): return name.endswith(_STATE_SUFFIXES) and not _is_command(name)
```

النية سليمة (منع إعادة أمر تنفيذ = تنفيذ مزدوج). لكن المطابقة الجزئية تصطاد أحداث حالة بريئة.

## خمسة أحداث حالة لا تُعاد أبداً — بصمت

| الحدث | المطابقة | المنتج | المستهلكون |
|---|---|---|---|
| `decision.eligibility.buy.state` | `.buy` | 455 قرار_الشراء | 2 |
| `decision.eligibility.sell.state` | `.sell` | 456 قرار_البيع | 2 |
| `liquidity.buyside.state` | `.buy` | 252 سيولة_الشراء | 2 |
| `liquidity.sellside.state` | `.sell` | 253 سيولة_البيع | 2 |
| `system.commands.state` | `command` | 901 بوابة_الأوامر | 0 |

## لماذا هذا هو الاكتشاف الأهم

`decision.eligibility.buy.state` و`decision.eligibility.sell.state` هما بالضبط البيانات التي تجيب:

> **«لماذا لا توجد صفقة؟»** — §18 من الدستور، السؤال الثاني من الأسئلة الأربعة

اللوحة مشترك **متأخر دائماً** (تُفتح بعد تشغيل النظام). المشترك المتأخر يستلم آخر حالة عبر `_last_event` — لكن هذه الأحداث **لا تُخزَّن أصلاً**، فلا شيء يُعاد.

النتيجة عند فتح اللوحة: خانة الأهلية فارغة إلى أن يتغيّر القرار من تلقائه. وقد لا يتغيّر لساعات.

**السؤال الرئيسي في المشروع كله مبني على حدثين يرفض الناقل إعادتهما.**

وبنفس المنطق `system.commands.state` — حالة بوابة الأوامر نفسها — لا تصل اللوحة عند الفتح.

## الإصلاح

استبدال المطابقة الجزئية بقائمة صريحة، أو بعلامة في المانيفست (`replayable: false`) بدل تخمين من الاسم. هذا تعديل نواة — لكنه **إصلاح عيب**، لا إضافة ميزة، ويستحق GAP بدرجة P0.

# 5. GAP-0002 محسوم — لا يوجد API بين الحوكمة و901

المسار الفعلي **صندوق بريد SQLite**، لا استدعاء شبكي:

```text
UI
 └─> POST /gov/...                       governance/server.py
      └─> queue_command()                server.py:719
           └─> INSERT INTO commands      var/governance/commands.db
                (action, operator, requested_at, payload_json)
                status = 'PENDING'
                                          ── حدود العملية ──
 901 على نبضة SYS_SECOND                  atoms/901/atom.py:215
      └─> SELECT ... WHERE status='PENDING' ORDER BY id LIMIT 20
           └─> await publish(event, body)          atom.py:352
                └─> UPDATE status='DONE'           atom.py:362
```

الإعداد: `max_age_s: 120` · `batch_limit: 20` · `db_path: var\governance\commands.db`

## ثلاث نتائج معمارية

**١. لا مسار لنتيجة الأمر.**
`command-result.schema.json` يفترض استجابة. لا توجد. الحوكمة تُرجع `{"stage":"queued"}` فوراً وتنتهي. النتيجة الحقيقية تُكتب في عمود `status` داخل قاعدة بيانات، وليس لها ناقل يعيدها للواجهة. **عقد النتيجة يحتاج مسار قراءة جديداً بالكامل** — استطلاع الـDB أو حدث `.state` من 901.

**٢. نافذة تنفيذ مزدوج مفتوحة هيكلياً.**
النشر يحدث **قبل** ختم `DONE` (352 قبل 362). أي انهيار بينهما يترك الصف `PENDING` فيُعاد إرساله في النبضة التالية.

وهذا ليس افتراضاً — التعليق في `atom.py:157-160` يوثّق أن الحادثة **وقعت فعلاً**:

> «counting blew up AFTER the command was published and BEFORE the row was stamped DONE — leaving it PENDING and re-dispatched every pulse»

عولج سبب واحد (انحراف عدّاد)، والنافذة الهيكلية باقية.

**٣. خبر جيد — مفتاح المنع موجود.**
`atom.py:350` يحقن `command_id` في جسم الحدث المنشور مع `operator` و`origin` و`reason`. أي أن مفتاح إلغاء التكرار **موجود على الناقل**.

(لم أتحقق بعد هل المستهلكون يستعملونه فعلاً في إلغاء التكرار — هذا فحص منفصل.)

# 11. الخلاصة

الوثيقتان بُنيتا على فرضيات معقولة، والجرد أثبت أن **معظمها صحيح في الاتجاه وخاطئ في التفاصيل**:

- بنية الناقل قوية فعلاً كما وُصفت — لكن غلافها نصف ما افترضته الوثيقة
- `901` بوابة الأوامر فعلاً — لكن عبر ملف، لا API، وبلا مسار عودة
- الفصل بين الحالة والأمر موجود فعلاً — لكن بـheuristic نصّي يكسر خمسة أحداث، منها حدثا السؤال الرئيسي
- الحمايات موجودة أكثر مما ظُنّ (`governance/checks/`) — والعقود غائبة أكثر مما ظُنّ (صفر schema)

**الخطوة التالية الوحيدة المستحقة: جرد الحمولات من `atom.py` للمنتجين الفعليين للأحداث التي تحتاجها النماذج الثلاثة الأولى** (`SystemPosture`, `DecisionPosture`, `RiskPosture`) — لا الـ226 كلها. هذا يحوّل النماذج الثلاثة من أسماء إلى عقود، ويثبت المعمارية على شريحة واحدة.
