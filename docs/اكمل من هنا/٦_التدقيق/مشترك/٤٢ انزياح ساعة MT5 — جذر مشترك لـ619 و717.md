# انزياح ساعة MT5 — جذر مشترك لـ#619 و#717

**تاريخ القياس:** 2026-08-28
**نوع الورقة:** تدقيق مُقاس من الحدث الحيّ + كود المصدر — لا اجتهاد. المشروع مجمّد، صفر تعديل.

---

## الاكتشاف — رقم حاسم

**من حدث `platform.account.state` الحيّ (ذرّة #619):**
```json
{
  "measured_at": 1787889368,
  "age_s": -157.97928380966187,
  "stale": true,
  "max_age_s": 300
}
```

**`age_s` سالب** — يعني طابع وقت EA (`updated_at`) **متقدّم عن الوقت الرسميّ للمشروع بحدود 158 ثانية (2.6 دقيقة).**

---

## السلسلة السببيّة الكاملة

```
منصّة MT5 (EA "QUANT_NQ" v3.10) تكتب account_v2 بطابع وقتها المحليّ
        ↓
ساعة المشروع الرسميّة (#3 Clock، #608 NTP) SYNCED فعليًّا — انحراف NTP ~95-100 ملّي ثانية فقط
        ↓
الفارق: طابع EA − الوقت الرسميّ ≈ +158 ثانية  (EA بالمستقبل نسبةً للمشروع)
        ↓
كود #619 (atom.py):  stale = age_s is None OR age_s < 0 OR age_s > max_age_s
                       ← عمر سالب = "بالمستقبل" = يُعتبر غير موثوق تلقائيًّا
        ↓
#619 يرجع ACCOUNT_STATE_STALE **رغم أنّ البيانات فعليًّا حيّة تمامًا**
      (البيانات مطابقة لشاشة MT5 بالضبط: رصيد 588.27$ في الاثنين)
```

**هذا نفسه، على الأرجح، جذر مشكلة `#717 Trading Data Integrity: ROWS_IN_THE_FUTURE`
الموثّقة سابقًا بورقة ٣٨ بلا تفسير حينها** — كلا الذرّتين تقيسان "هل طابع الوقت
القادم من MT5 منطقيّ مقابل الساعة الرسميّة؟"، وكلاهما يرى نفس الانزياح.

---

## السبب الجذريّ الحقيقيّ

**ليس عطلًا بكود المشروع ولا بالـEA نفسه (الـEA حيّ، متّصل، يكتب بيانات صحيحة —
مؤكَّد من لقطتي شاشة المالك المباشرتين).** السبب: **ساعة الجهاز/الخادم الذي
تعمل عليه منصّة MT5 غير متزامنة مع نفس مرجع NTP الذي يزامن عليه المشروع** —
انزياح ثابت تقريبًا حول 150-160 ثانية بين القياسين المتتاليين (لقطتا الشاشة
أظهرتا أرقام "ت" متغيّرة بمرور الوقت، متّسقة مع ساعة تمشي بمعدّل مختلف قليلًا
لا مجرّد قفزة واحدة).

---

## الحلّ (بيد المالك، بعد فكّ التجميد أو خارج الكود كليًّا)

**لا يحتاج تعديل كود بالضرورة** — الحلّ الأقرب: **مزامنة ساعة نظام التشغيل
اللي MT5 شغّال عليه مع NTP فعليًّا** (خدمة Windows Time). هذا يصلح `#619`
و`#717` معًا دفعة واحدة لأنّهما نفس القياس.

**إن تعذّر تصحيح الساعة فعليًّا:** يحتاج قرار مالك لاحقًا هل يُعاد النظر بمنطق
`age_s < 0 ⇒ stale` ليتسامح مع انزياح صغير معروف بدل الرفض المطلق — **قرار
هندسيّ يخصّ المالك، لا اجتهاد.**

## ⚠️ تصحيح (٢٠٢٦-٠٨-٢٨، بعد فحص المالك المباشر) — التفسير الأول كان غلط

**المالك شغّل `w32tm /stripchart` بنفسه:** انحراف ساعة الويندوز = **103 ملّي ثانية
فقط** — سليمة تمامًا. **فرضيّة "ساعة MT5/الويندوز غير متزامنة" خطأ، وأُسحب.**

**القياس الصحيح (فحصين متتاليين على نفس الحدث):**
```
الفحص ١:  age_s = -157.97   (measured_at=1787889368)
الفحص ٢:  age_s = -305.97   (measured_at=1787889932، بعد ~9.4 دقائق واقعيّة)
```
**الفارق كبر ~148 ثانية خلال ~564 ثانية واقعيّة — أي طابع EA يتقدّم بمعدّل
≈0.26 ثانية لكل ثانية حقيقيّة. هذا ليس انزياح ساعة (ثابت)، بل معدّل غير طبيعي
تمامًا لأي ساعة عتاد حقيقيّة.**

**وبفحص كود الساعة الرسميّة (`clock/clock.py`):** `max_accepted_offset_s=5.0`
(النطاق المقبول لعيّنة NTP)، وعيّنة المشروع الفعليّة (~95 ملّي ثانية) مقبولة
براحة — أي **الوقت الرسميّ للمشروع (`official_time`) دقيق فعلًا**، يطابق نتيجة
`w32tm` المالك تمامًا.

**الفرضيّة الجديدة (غير مؤكَّدة، تحتاج تحقّقًا إضافيًّا):** طابع `updated_at`
اللي EA بيكتبه لسّا غير مشتقّ من ساعة حقيقيّة — **يرجّح إنّه مشتقّ من طابع
آخر تِكّة بتغذية محاكاة/تجريبيّة سريعة** (نفس نمط تقارير الـharness السابقة:
تِكّات محقونة بمعدّل أسرع من الزمن الحقيقيّ)، لا من ساعة نظام فعليّة. **هذا
تخمين مبنيّ على القياس أعلاه، لا إثبات — يحتاج فحص مصدر `updated_at` داخل
منطق الـEA نفسه لتأكيده.**

## ✅ السبب الجذريّ مؤكَّد بالكود — `mt5/QUANT_NQ.mq5` سطر 775-776

```cpp
"UPDATE account_v2 SET updated_at=%d WHERE account_id='%s';",
(int)TimeGMT(), ...
```

**الـEA بيستعمل `TimeGMT()` — دالّة MQL5 اللي بتحسب GMT اعتمادًا على ساعة
*خادم الوسيط* (trade server) وفرق منطقتها الزمنيّة، لا ساعة الويندوز المحليّة
إطلاقًا.** هذا يفسّر بدقّة ليش تصحيح NTP لساعة الويندوز (اللي أثبته المالك:
103 ملّي ثانية فقط) **ما كان له أي أثر متوقَّع من الأساس** — العلاقة بين
`updated_at` وساعة الجهاز مقطوعة كليًّا بتصميم الـEA.

**السبب الجذريّ النهائيّ:** **ساعة خادم الوسيط التجريبيّ نفسه**
(`ICMarketsSC-Demo` / `Raw Trading Ltd`) **تنجرف عن الوقت الحقيقيّ بمعدّل
متسارع** (≈0.26 ثانية/ثانية حقيقيّة، من القياسين المسجَّلين أعلاه) — أمر
خارج تحكّم المشروع أو الجهاز المحليّ بالكامل، وشائع بخوادم الحسابات
التجريبيّة (Demo) اللي أحيانًا تُشغَّل بمحاكاة مُسرَّعة.

1. **تجاهل الأمر** إن كان الحساب تجريبيًّا مؤقّتًا لن يُستخدم بجدّيّة.
2. **التواصل مع الوسيط** بخصوص دقّة ساعة خادم `ICMarketsSC-Demo`.
3. **قرار هندسيّ لاحق:** تعديل منطق `age_s < 0 ⇒ stale` بذرّة #619 ليتسامح

   المالك بعد فكّ التجميد، ودراسة أثره على الحماية (كان هذا الفرع أصلًا حارسًا
   ضدّ تلاعب/قفزة ساعة، فتخفيفه قرار أمان لا تفصيل بسيط).
