# تشريح عصبي دقيق لمرحلة A — كون العملات قبل الحواس

**التاريخ:** 2026-08-26  
**الحالة:** **محدّث بعد تصحيح المالك — Phase A Feed Only**  
**النطاق:** الكريبتو فقط داخل `atoms_crypto/`  
**مهم:** النسخة الأولى من هذا التحليل كانت تشرح دمج ASMAR وحواسًا فوق الألف. تم إلغاء ذلك من التنفيذ. لا يوجد مشروع كريبتو سابق في هذا الإصدار؛ المصدر الوحيد هو `1001` و`1002`.  
**القاعدة:** لا تغيير على الفوركس، ولا حواس، ولا قرار تداول، ولا استبدال قائمة بثلاثة أسطر وكأنها كون كامل.

---

## الخلاصة قبل التفاصيل

النص المرفق ليس طلبًا من نوع:

```text
بدّل BTC_USDT و ETH_USDT و SOL_USDT بثلاثة رموز أخرى
```

وليس طلبًا من نوع:

```text
أضف بطاقة صغيرة إلى اللوحة وانتهينا
```

هو **طبقة تحكم جديدة تسبق التغذية والحواس**:

```text
MEXC Universe Snapshot
        ↓
Normalize + Validate
        ↓
Liquidity / Spread / Native / Range / Manual
        ↓
Core Ring + Outer Ring
        ↓
Dynamic Membership State
        ↓
MEXC Feed Subscription
        ↓
Data + Senses
        ↓
Crypto Dashboard
```

إذًا القرار الصحيح هو:

> **نحدّث الورقة أولًا لتثبيت عقد «كون العملات»، ثم نزيل القوائم الثلاث الثابتة من التشغيل، ثم نضيف لوحة الكون التي تعرض الحقيقة الناتجة. لا نبدأ من اللوحة ولا نضع رموزًا جديدة مكان الرموز القديمة مباشرة.**

## ١ — أين الكذبة الحالية في الكود؟

في النسخة الموحّدة الحالية توجد قائمة ثابتة في مكانين تشغيليين:

```text
atoms_crypto/1620_مصدر_MEXC/manifest.yaml
atoms_crypto/1621_مصدر_MEXC_REST/manifest.yaml
```

والقائمة الحالية هي:

```yaml
symbols:
  - BTC_USDT
  - ETH_USDT
  - SOL_USDT
```

كما أن الحاسة `1160` تحمل قائمة ومرجعًا افتراضيين من نفس العائلة:

```text
atoms_crypto/1160_تزامن_السوق/manifest.yaml
atoms_crypto/1160_تزامن_السوق/atom.py
```

والسلوك الحالي هو:

1. `1620` يقرأ الرموز من الـManifest مرة واحدة عند `initialize`.
2. `1620` يفتح اشتراكات WebSocket لهذه الرموز فقط.
3. `1621` يقرأ الرموز من الـManifest مرة واحدة عند `initialize`.
4. `1621` يستطلع REST لهذه الرموز فقط.
5. `1160` يستخدم `BTC_USDT` كمرجع، ويقارن قائمة ثابتة.
6. اللوحة تستنتج الرموز من الأحداث التي وصلت إليها، لا من سجل كون رسمي.

هذه ليست «قائمة قابلة للتبديل». هذه **حدود تشغيل محفورة وقت الإقلاع**.

### النتيجة

إذا بدّلنا الرموز الثلاثة يدويًا داخل الـManifest، حصلنا على:

```text
Static List v2
```

وليس:

```text
Dynamic Asset Universe
```

وإذا بدّلناها من اللوحة فقط، تصبح اللوحة مصدرًا خفيًا للحقيقة وتبدأ التغذية
بقراءة إعداد لا يمر بعقد أو نسخة أو سبب أو تدقيق. هذا ممنوع معماريًا.

## ٢ — ما الذي لا تنفذه النسخة الحالية من Phase A؟

النص يطلب خمسة فلاتر وبابين دوّارين. الكود الحالي لا يملك مديرًا واحدًا ينفذها.

| المطلوب | وضعه الحالي |
|---|---|
| طلب Ticker شامل لكل العقود | غير موجود كطبقة كون؛ المصدران يعملان بقائمة ثابتة |
| حجم تداول 24 ساعة بالدولار | لا يوجد عقد موحد يثبت وحدة القياس والمحوّل إلى USD |
| Spread حقيقي ≤ 3 نقاط | لا توجد بوابة كون تحسبه من Bid/Ask وTick Size |
| استبعاد الأصول غير الأصلية | لا توجد مصنّفات/أسباب رفض رسمية |
| Range يومي ≤ 20% | لا توجد بوابة نطاق يومي قبل اختيار العضوية |
| تثبيت/طرد يدوي | لا يوجد سجل عضوية خاص بالكون في مسار الكريبتو |
| حلقتان Core/Outer | لا توجد عضوية `ring` منشورة للناقل |
| دوران مجدول | لا توجد آلة حالات للدخول/الخروج بصمود وفشل |
| حماية الصفقة المفتوحة | لا يوجد ربط رسمي بين عضوية الكون وحالة المركز |
| تحديث التغذية بلا إعادة تشغيل | `1620` و`1621` يقرآن القائمة عند الإقلاع فقط |
| لوحة تعرض سبب الرفض | اللوحة تعرض ما وصل من السوق، لا قرار الكون |

**الحكم:** لا يجوز تعديل أرقام الرموز الثلاثة قبل بناء هذه الطبقة؛ وإلا نكون
قد أخفينا المشكلة خلف قائمة أخرى.

## ٣ — العقد الصحيح: Universe Manager

نحتاج ذرة جديدة خاصة بالكريبتو، رقمها فوق الألف. الرقم المقترح للتصميم:

```text
1001 — مدير كون الأصول
```

هذا الرقم **مقترح للحجز فقط**؛ يثبت نهائيًا داخل خريطة الترقيم قبل الكتابة.

### مسؤوليات الذرة

`1001` لا تحلل دخولًا ولا تشتري ولا تبيع. مهمتها الوحيدة:

1. أخذ لقطة Ticker شاملة من مصدر واحد.
2. توحيد الحقول ووحدات القياس.
3. تطبيق الفلاتر الخمسة.
4. قراءة الاستثناءات اليدوية المعتمدة.
5. بناء عضوية Core وOuter.
6. إدارة آلة الدوران.
7. نشر Snapshot واحد موثّق.
8. نشر تحديث عضوية عندما يتغير الكون.

### ما لا تفعله

- لا تدخل في قرار الحواس.
- لا تصوّت على شراء/بيع.
- لا تعدل `RISK_DIAL`.
- لا تقرأ قرار الفوركس.
- لا تكتب إلى حساب MEXC.
- لا تجعل اللوحة تكتب القائمة مباشرة.

## ٥ — تشريح الفلاتر الخمسة

### الفلتر ١: السيولة

المطلوب:

```text
Core  ≥ 50,000,000 USD notional / 24h
Outer ≥ 10,000,000 USD notional / 24h
```

لكن يجب تثبيت نقطة خطيرة قبل التنفيذ:

> لا يجوز استعمال حقل اسمه `volume24` واعتباره دولارًا بلا إثبات.

قد يكون الحقل عقودًا أو وحدات أصل أو قيمة اسمية قبل معامل العقد. لذلك العقد
يجب أن يعلن:

```text
raw_value
raw_unit
contract_multiplier
quote_currency
usd_conversion_source
liquidity_usd_24h
```

إذا تعذر تحويل القيمة إلى USD بصدق، يكون السبب:

```text
LIQUIDITY_UNIT_UNKNOWN
```

ويُرفض الرمز من الاختيار الآلي بدل اختراع رقم.

### الفلتر ٢: السبريد

`≤ 3 ن.أ` لا يعني «ثلاثة سنتات» ولا «0.03 من السعر». يجب حسابه على أساس
أصغر حركة مسموحة للعقد:

```text
spread_ticks = (ask - bid) / price_tick_size
```

والحالات:

```text
bid/ask ناقصان       → SPREAD_UNKNOWN
price_tick_size ناقص → TICK_SIZE_UNKNOWN
spread_ticks > 3     → SPREAD_TOO_WIDE
```

لا يجوز تمرير الرمز إلى Core بسبب نقص بيانات السبريد.

### الفلتر ٣: كريبتو أصيل

لا يكفي فحص اسم الرمز عبر كلمات مثل `GOLD` أو `SILVER`. التصنيف يجب أن يعتمد
على Metadata المصدر:

```text
instrument_type
contract_category
base_asset
quote_asset
underlying_type
```

وتكون النتيجة صريحة:

```text
NATIVE_CRYPTO
TOKENIZED_COMMODITY
TOKENIZED_EQUITY
INDEX
UNKNOWN
```

كل من `TOKENIZED_COMMODITY` و`TOKENIZED_EQUITY` و`INDEX` و`UNKNOWN` خارج الكون
الآلي. الاستثناء اليدوي لا يمحو سبب التصنيف؛ بل يسجل أنه Override معتمد.

### الفلتر ٤: سقف المدى

يجب تثبيت المعادلة قبل الكود. المقترح:

```text
daily_range_pct = (high_24h - low_24h) / reference_open_24h × 100
```

لكن `reference_open_24h` يجب أن يكون حقلًا معروف المصدر. إذا لم يكن متاحًا،
لا نبدله بـ`lastPrice` صامتًا. الحالة تصبح:

```text
DAILY_RANGE_UNKNOWN
```

والقاعدة:

```text
range > 20% → RANGE_TOO_WIDE
```

الرمز المرفوض لا يختفي؛ يظهر في `rejected` مع الرقم الذي أسقطه.

### الفلتر ٥: اليدوي

اليدوي ليس تعديلًا مباشرًا على `symbols` في Manifest. نحتاج جدولًا دائمًا:

```text
manual_membership(
    symbol,
    decision: ALLOW | DENY | NEUTRAL,
    scope: CORE | OUTER | BOTH,
    reason,
    operator,
    command_id,
    approved_at,
    expires_at,
    version
)
```

الأولوية:

```text
DENY اليدوي       → يطرد
ALLOW اليدوي      → يسمح بالمرور بعد فحوص السلامة الأساسية
NEUTRAL           → يترك القرار للفلاتر
```

وحتى `ALLOW` لا يجب أن يتجاوز نقص الهوية أو نقص Tick Size أو نقص وحدة
السيولة؛ اليدوي يغيّر العضوية المسموحة، لا يخلق بيانات غير موجودة.

## ٦ — الحلقتان ليستا قائمتين ثابتتين

المطلوب:

```text
Core   ≈ 12
Outer  ≈ 15
```

هذه أرقام سعة/هدف وليست أسماء مقدسة. يجب أن تكون مدخلات محكومة:

```text
core_target_count
outer_target_count
core_min_liquidity
outer_min_liquidity
```

الاختيار داخل كل حلقة يحتاج ترتيبًا معلنًا، مثل:

```text
1. اجتياز الفلاتر الصلبة
2. استبعاد DENY اليدوي
3. تطبيق ALLOW اليدوي ضمن حدود السلامة
4. ترتيب بالسيولة الموثوقة
5. كسر التعادل بالسبريد ثم حداثة البيانات
6. أخذ العدد المستهدف
```

إذا لم يوجد عدد كافٍ، لا نملأ الفراغ برموز ضعيفة كي يصبح الرقم 12 أو 15.
النتيجة الصحيحة:

```text
core_count = 8
reason = NOT_ENOUGH_QUALIFIED_ASSETS
```

## ٧ — الفرق الحقيقي بين Core وOuter

### Core

```text
market tick
market candle
market depth
market trade
open interest
funding
premium
كل الحواس
كل القياسات المسموح بها
```

### Outer

```text
market tick الضروري
spread gate
fuel / open interest / funding / premium
economic gate
مراقبة صحة العضوية
```

ولا يجب أن تصل Outer إلى الحواس الغالية بالخطأ. مجرد وضع:

```json
{"ring": "outer"}
```

داخل الحمولة لا يكفي، لأن الحواس الحالية تشترك في أحداث عامة مثل:

```text
market.candle
market.depth
market.trade
```

إذا بقيت الاشتراكات كما هي، ستستقبل Outer نفس الحسابات الثقيلة، وتصبح الحلقة
الخارجية اسمًا على بطاقة لا فرقًا في التشغيل.

### الحل الهندسي

إما:

```text
أحداث نطاقية:
market.core.candle
market.outer.fuel
market.core.depth
```

أو:

```text
Policy gate قبل كل حاسة
الحاسة تعلن هل تقبل CORE أو OUTER
```

المهم أن يكون الفرق قابلًا للفحص، لا اتفاقًا شفهيًا.

## ٨ — الباب الدوّار هو آلة حالات

لا نكتب «يدخل بعد ٢–٣ أيام ويخرج بعد ٣–٧ أيام» ثم نترك المعنى معلقًا.
يجب تحديد القيم المحكومة:

```text
entry_resilience_days = 2 أو 3 بقيمة معتمدة
exit_failure_days = 3 أو 7 بقيمة معتمدة
```

وحالات العضوية:

```text
CANDIDATE
PROBATION
CORE_ACTIVE
OUTER_ACTIVE
EXIT_PENDING
HELD_OPEN_POSITION
EXITED
```

### الدخول

```text
QUALIFIED
→ لا يكفي مسح واحد
→ يدخل PROBATION
→ يصمد مدة الدخول
→ يصبح ACTIVE
```

### الخروج

```text
ACTIVE
→ يفشل فلترًا صلبًا
→ EXIT_PENDING
→ إذا عاد قبل نهاية نافذة السماح يبقى
→ إذا استمر الفشل يخرج من الانتباه الجديد
```

### الصفقة المفتوحة

إذا خرج الرمز من الكون:

```text
NEW_ENTRY = BLOCKED
MANAGEMENT = CONTINUES
CLOSE = لا يحدث بسبب العضوية وحدها
```

هذه القاعدة يجب أن تكون في عقد إدارة المركز، لا في واجهة المستخدم فقط.

## ٩ — أين تدخل «صفقة واحدة كروس×٢٠»؟

هذه ليست قاعدة كون العملات. الكون يحدد:

```text
ما الرموز المؤهلة؟
أي حلقة؟
أي بيانات تصلها؟
```

أما:

```text
صفقة واحدة
الميزانية
الحجم
المخاطرة
```

فمكانها:

```text
Portfolio / Risk / Position Gate
```

وإلا سيصبح `Universe Manager` مسؤولًا عن السوق وعن المحفظة وعن التنفيذ،
وتنهار الحدود بين الطبقات.

المعلومة الوحيدة التي يحتاجها الكون من المحفظة هي:

```text
هل لهذا الرمز مركز مفتوح؟
```

حتى يفعّل `HELD_OPEN_POSITION` ويحظر الدخول الجديد دون قتل الإدارة القائمة.

لوحة الكريبتو الحالية تعرض الرموز التي رآها مخزن الواجهة. هذا غير كافٍ. يجب
إضافة تبويب واضح:

```text

```

### شريط الحالة

```text
آخر مسح
Universe Version
عمر اللقطة
المصدر
حالة المصدر
Core count
Outer count
رفض اليوم
```

```text
الرمز
السيولة USD/24h
Spread ticks
Range %
نوع الأصل
عمر البيانات
الحالة
النسخة
```

### جدول Outer

```text
الرمز
السيولة
Spread Gate

```

### جدول الرفض


```text

تحت الاختبار
خروج معلق
محمي بسبب مركز مفتوح
```

### التحكم اليدوي

اللوحة لا تعدّل القائمة مباشرة. كل زر يرسل أمرًا موثقًا:

```text

→ command_id
→ operator
→ universe.override.command
→ الذرة 1001
→ universe.snapshot.state جديد
```

ولا توجد في لوحة الكريبتو أزرار شراء/بيع أو زر تنفيذ مخفي.

## ١١ — ما الذي يتغير في الملفات؟

هذه هي خريطة التنفيذ الصحيحة بعد اعتماد التحديث:

```text
1. إضافة ذرة Universe Manager فوق 1000.
2. إضافة عقد Snapshot وMembership وReject وRotation.
3. إضافة تخزين عضوية وOverrides منفصل للكريبتو.
4. تغيير 1620 ليقرأ Membership حيًا بدل قائمة Manifest.
5. تغيير 1621 ليقرأ Membership حيًا بدل قائمة Manifest.
6. تغيير 1160 ليقرأ reference/symbols من Snapshot بدل الثلاثة الثابتة.
7. إضافة Ring Policy حتى لا تصل Outer إلى كل الحواس.
8. إضافة حماية Open Position.
9. إضافة لوحة كون العملات.
10. إزالة BTC/ETH/SOL من Config التشغيل.
11. إبقاء الرموز داخل اختبارات الوحدة فقط كبيانات اختبار.
12. اختبار تحديث العضوية دون إعادة تشغيل.
```

### ما لا نفعله

```text
لا نبدّل القائمة الثلاثية بقائمة ثلاثية أخرى.
لا نجعل React مصدر الحقيقة.
لا نضع شروط السيولة داخل 1620 وحده.
لا نستخدم 901 الخاص بالفوركس للكريبتو.
لا نربط المخاطرة بين المسارين.
لا نرسل أمر تداول من Universe Manager.
لا نعتبر وصول الرمز إلى اللوحة دليلًا على عضويته.
```

## ١٢ — اختبارات القبول قبل حذف القائمة الثابتة

### اختبار المصدر

- طلب واحد شامل أو Snapshot واحد من طبقة الكون.
- لا توجد قائمة رموز ثابتة في التشغيل.
- فشل المصدر ينتج `UNIVERSE_SOURCE_STALE` ولا يبني عضوية جديدة بصمت.

### اختبار الفلاتر

لكل رمز مرفوض:

```text
سبب واحد أو أكثر معروف
القيمة الخام محفوظة
وحدة القياس محفوظة
وقت القياس محفوظ
Universe Version محفوظ
```

### اختبار الديناميكية

```text
تغيير نتيجة ticker
→ مسح جديد
→ universe_version جديد
→ membership state جديد
→ 1620 يبدّل الاشتراكات دون restart
→ 1621 يبدّل polling دون restart
```

### اختبار الحلقات

```text
رمز Core يستقبل الحواس كلها.
رمز Outer لا يستقبل الحواس الغالية.
رمز خرج من الكون لا يولد دخولًا جديدًا.
مركز مفتوح لا يُقتل بسبب الخروج من القائمة.
```

### اختبار اليدوي

```text
DENY يمنع الدخول
ALLOW لا يتجاوز نقص البيانات الحرجة
إعادة التشغيل تحفظ Override
اللوحة تعرض operator وcommand_id
```

### اختبار اللوحة

```text
لا يظهر BTC/ETH/SOL كقائمة مقدسة.
اللوحة تعرض العدد الفعلي، ولو كان صفرًا.
سبب الرفض ظاهر.
الحلقتان ظاهرتان.
عمر Snapshot ظاهر.
الاتصال المقطوع ظاهر كحالة، لا كقائمة قديمة سليمة.
```

## الحكم النهائي

الرموز الثلاثة الحالية ليست شيئًا نبدله؛ هي **أثر تجريبي مؤقت** يجب إخراجه من
مسار التشغيل.

التحديث الصحيح هو:

```text
ورقة Phase A جديدة
        ↓
Universe Manager
        ↓
Membership Snapshot
        ↓
Dynamic 1620 / Dynamic 1621 / Dynamic 1160
        ↓
Crypto Dashboard: Universe tab
```

والجواب المباشر على السؤال:

> **نعم، يجب تحديث لوحة مشروع الكريبتو لتعرض كون العملات والحلقتين والفلاتر
> والدوران. لكن لا، لا نستبدل رمز العملات الثلاثة مباشرة بهؤلاء. نضيف مدير
> كون رسميًا، ثم تصبح الرموز ناتجًا حيًا منه، وتصبح اللوحة مرآة لهذا الناتج.**

أي تنفيذ قبل تثبيت هذا العقد سيكون ترقيعًا، حتى لو بدا أن الأرقام تبدلت
واللوحة صارت تعرض أسماء جديدة.
