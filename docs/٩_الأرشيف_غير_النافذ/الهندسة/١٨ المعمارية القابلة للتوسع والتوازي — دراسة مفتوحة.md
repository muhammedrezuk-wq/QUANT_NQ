## ٠ · تصحيح الاتجاه (المالك — ٢٦-٠٨ · يحكم بقية الورقة)

**المشكلة المنقولة الآن تغيّر الأولوية.**

**الجدار الحالي ليس** التوسع المستقبلي:
```text
حسابات كثيرة × رموز كثيرة × 1000 ذرة   ← جدار مستقبلي
```

**الجدار الحالي هو:**
```text
TICK
 ↓
شلّال تحليل كبير
 ↓
أحداث كثيرة
 ↓
نسخ لكل مشترك
 ↓
بث للوحة
 ↓
كل هذا على مسار مركزي
```

يعني النظام حاليًا **يحرق CPU بسبب طريقة تشغيله، لا بسبب حجم التداول.**

وهذا أهم؛ لأننا إذا بنينا «٦ طبّاخين» بطريقة غلط، ممكن **نوزّع المشكلة فقط:**
```text
طبّاخ 1 → ينسخ كثير
طبّاخ 2 → ينسخ كثير
...
طبّاخ 6 → ينسخ كثير
```
ويظل التصميم نفسه سيّئًا.

**القرار الهندسي الصحيح — هدف الورقة المفتوحة:**
> إزالة التسلسل المركزي والشلّال غير الضروري **أولًا**، ثم جعل المعمارية قابلة للتوسع.
> **وليس:** «نقسم العمل على ٦ أنوية وخلاص».

**الترتيب المعتمد:**
```text
1.  قياس حي
2.  تحديد أين يذهب CPU اليوم
3.  تحديد مسار التكة الكامل
4.  تحديد كل نسخ الحمولة
5.  تحديد كل Fan-out
6.  تحديد كل Global Lock / Serialization
7.  تصميم النواة الجديدة
8.  توزيع العمل على الـ6 Cores
9.  اختبار الحمل الحالي
10. 200 ذرة
11. 500
12. 1000+
```

**النقطة الأهم:** لا نقرّر أن ٦ طبّاخين هم الحل قبل القياس. الـ٦ أنوية هي **المورد المتاح**؛ أما المعمارية فهي التي تقرّر:
كم Worker؟ · ماذا يملك كل Worker؟ · ماذا يبقى مركزيًا؟ · ماذا يصبح Parallel؟ · أين توضع الذاكرة؟ · أين تُمنع النسخ؟ · أين نسمح بالـqueue؟ · أين يجب أن يكون التنفيذ synchronous؟ · أين يمكن أن يكون asynchronous؟

**وبالنسبة للـ119%:**
```text
OLD MEASUREMENT  ≠  CURRENT FACT
```
الرقم ١١٩٪ من قياس سابق قبل آخر التعديلات — **لا نبني عليه قرارًا نهائيًا.** نقيس الحالة الحالية أولًا. فإذا ظهر مثلًا:
```text
Router      18%
Copy        22%
Analysis    31%
Persistence  4%
Dashboard    9%
Other       16%
```
وقتها نعرف **وين نضرب بالمطرقة**. وإذا طلع الحمل اليوم مختلفًا تمامًا، **الورقة تتغير وفق الدليل** — وهذا بالضبط سبب أنها مفتوحة لا ورقة تنفيذ.

## ٠-ب · نتيجة القياس الحيّ — CURRENT FACT
**التاريخ:** ٢٦-٠٨-٢٠٢٦
**المصدر:** قياس حيّ py-spy
**الحالة:** CURRENT FACT

التوزيع الحالي لاستهلاك CPU:

| الحمل | CPU | الحكم |
|---|---:|---|
| نسخ الحمولة | **40.6%** | **الاختناق رقم 1** |
| التحليل الحقيقي | **16.4%** | الشغل المفيد |
| التخزين | **12.0%** | اختناق ثانوي مهم |
| الناقل Bus | **11.5%** | اختناق معماري مهم |
| بثّ اللوحة | **5.8%** | خارج Hot Path |
| Stamp | **2.9%** | كلفة سباكة |
| التغذية/الشبكة | **1.3%** | حمل صغير |
| قراءة العيارات | **0.6%** | لم تعد اختناقًا |
| UUID | **0.7%** | لم يعد اختناقًا |
| Idle | **5.2%** | هامش متاح |

### الاستنتاج

**COPY = 40.6% هو الاختناق رقم 1 الحالي.**

التحليل الحقيقي = **16.4%** فقط.

إذن المشكلة الحالية ليست أن التحليل الحسابي يستهلك معظم CPU، بل أن نموذج نقل الأحداث يستهلك الجزء الأكبر من القدرة:

**COPY + BUS + STORAGE + DASHBOARD + STAMP + UUID + OTHER**

أي أن إعادة تصميم **Event Transport + Ownership + Memory + Hot/Cold Path** تسبق زيادة عدد Workers.

### ملاحظة المقارنة

القياس السابق: `COPY = 33.9%` · القياس الحالي: `COPY = 40.6%`

لا تُفسَّر الزيادة كـ regression أو تحسن/تدهور مباشر إلا إذا كانت ظروف القياسين متطابقة. لكن الثابت بين القياسين هو:

> **COPY بقي الاختناق رقم 1.**

لذلك هذا هو الجدار المعماري الأول الذي يجب أن يعالجه التصميم الجديد.

### ما لم يعد يمثل جدارًا رئيسيًا

`approved_value = 0.6%` · `UUID = 0.7%` — لم يعودا أهداف تحسين أولية في التصميم.

### ترتيب الأولويات الحالي

1. **Event Copy / Payload Ownership**
2. **Event Bus / Fan-out**
3. **Persistence / Cold Path**
4. **Dashboard / Output**
5. **Stamp**
6. **Compute Parallelism**

ولا يجوز عكس هذا الترتيب بإضافة Workers قبل إزالة الاختناق المركزي في النقل.

## ٠-ج · تنقيحات المالك على الاتجاه (٢٦-٠٨ · بعد القياس)

1. **المشكلة الأساسية = نموذج نقل الأحداث نفسه** (Event Transport Model)، لا حساب CPU وحده. القياس §٠-ب يثبتها: النسخ + الناقل + البثّ + UUID كلّها من **نموذج النقل**، ومجتمعةً تفوق التحليل الحقيقي أضعافًا.
2. **`ACCOUNT × SYMBOL` مرشّح لا حلّ.** لا يُكتب «= الحل» قبل دراسة الملكية والجدولة. البدائل: `partitioned workers` · `account × symbol ownership` · `dynamic scheduler` · أو خليط.
3. **تصحيح §١٠:** الهدف ليس `Dropped = 0` مطلقًا (قاسٍ معماريًّا)، بل **لا فقد صامت**: عند overload النظام يعرف ماذا يفعل ويسجّل الحدث ولا يرمي بلا علمنا؛ والأحداث غير الحرجة قد تكون لها سياسة مختلفة **يحدّدها العقد لاحقًا، لا هنا مسبقًا**.
4. **«٦ طبّاخين» ليست الهدف.** الهدف: `6 Cores → أفضل توزيع للعمل → بلا Central Bottleneck` — لا `6 Cores → 6 Cookers`. المعمارية المثلى قد تكون مثلًا 4 عمّال حساب + مسار I/O + مسار تحكم، أو نموذجًا آخر تمامًا.

**الخطوة التالية المعتمدة (قياس/تشريح، ليست بناء):** رسم `CURRENT ARCHITECTURE` من الكود الفعلي — من لحظة وصول التكة إلى آخر مستهلك، مع كل نسخة · queue · lock · publish · persistence · ووقت كل مرحلة. بعدها فقط يُصمَّم التوزيع على أساس حقيقي بدل إعادة بناء المشكلة بشكل جديد.

## ٠-د · CURRENT ARCHITECTURE — مرسومة من الكود الفعلي + القياس الحيّ (٢٦-٠٨)

**من لحظة وصول التكة إلى آخر مستهلك. النِّسَب = قياس §٠-ب. البنية = من الكود. الشلّال = مُستنتَج من عدد المحلّلين (15) + الأقسام + القرار.**

```text
                    السوق (cTrader / MT5)
                          │  HTTP / SSL polling
        ┌─────────────────┴──────────────────┐
        │  خيوط التغذية (ThreadPool · off-loop)│  ~3% CPU
        │  _fetch → http_get_json → ssl.read   │  (لا تزاحم الحلقة)
        └─────────────────┬──────────────────┘
                          │ publish(market.tick) → تُسلَّم للحلقة
   ═══════════════════════╪═══════════════════════════════════════
   ║   الحلقة الرئيسية الواحدة (asyncio · خيط واحد)                 ║ ★ نقطة التسلسل المركزية
   ║   كل ما تحت هنا على خيط واحد — والـGIL يمنع توازي حساب بايثون   ║
   ═══════════════════════╪═══════════════════════════════════════
                          ▼
              613 market.tick ─► 112 tick.validated
                          │
                          ▼  كل publish() يعمل:
             ┌──────────────────────────────────────────┐
             │ _fast_copy (نسخة أولى للحمولة)             │
             │ uuid4() event_id                    ~3.7% │
             │ _classify_name (مصنَّف محفوظ)              │
             │ لكل مشترك: _isolated_copy (pickle)  ~34% ★│ ← الجدار رقم 1
             │ _enqueue → صندوق بريد المعالج (queue 1024)│
             └──────────────────────────────────────────┘
                          │  الشلّال (fan-out): تكّة واحدة → عشرات الأحداث
        ┌─────────────────┼─────────────────┬──────────────────┐
        ▼                 ▼                 ▼                  ▼
   15 محلّل          أقسام 200-400     طبقة القرار         مشتركو الكل
   stamp_section     تجميع             451-458             (firehose)
   +approved_value ~5.6% · stamp ~3.1%
                          │
                          ▼  _consume مستهلك صناديق البريد ~12.3% (تسليم مرتّب · عزل · مهلة)
        ┌─────────────────┼─────────────────┬──────────────────┐
        ▼                 ▼                 ▼                  ▼
   بثّ اللوحة         التخزين            التحليل الحقيقي     asyncio خامل
   _broadcast→json    enforce_limits     live_analysis       ~4.9%
   ~6% → WebSocket    +gzip+fs-walk      +atom
                      ~10% (مش مطفيّ)     ~12% (الشغل المفيد الوحيد)
```

**القراءة المعمارية (حقائق):**
- **عملية واحدة · حلقة asyncio واحدة** (`run_core.py: asyncio.run`) = **نقطة التسلسل المركزية**. كل شيء عدا جلب الشبكة يجري على **خيط واحد**، والـGIL يمنع توازي حساب بايثون حتى في الخيوط.
- **التغذية وحدها off-loop** (خيوط) — سليمة، لا تزاحم.
- **لا قفل mutex عالمي** في المسار الساخن (صناديق البريد V3.0 شالت قفل-المعالج) — **التسلسل هو الخيط الواحد نفسه، لا قفلٌ صريح.**
- **النسخ** يحدث مرارًا لكل حدث: `_fast_copy` أولية + `_isolated_copy` **لكل مشترك** + نسخة `_last_event` + نسخ الإعادة للمشترك المتأخّر.
- **الطوابير:** صندوق بريد لكل معالج (سقف 1024، دمج LATEST_ONLY للحالات).
- **النموذج المركزي (النقل) ≈ 65%+** من الخيط الواحد (نسخ 34 + ناقل 12 + stamp/عيارات 9 + بثّ 6 + uuid 4)، مقابل **~12% تحليل حقيقي**.

**الاستنتاج:** الجدار ليس «عدد الأنوية» بل **نموذج النقل يجري كلّه على خيط تسلسل واحد**. أي توزيع على أنوية لا يشيل هذا النموذج = يوزّع نفس المشكلة (§٠-ج بند 1/4).

## ٠-هـ · الاعتماد والمحسوم (المالك — ٢٦-٠٨)

**الحكم: معتمدة كـ OPEN STUDY** — مرجع الدراسة المعمارية المفتوحة، **لا خطة تنفيذ**. الحالة تبقى حرفيًّا:
```text
ARCHITECTURE STUDY → OPEN → NO IMPLEMENTATION / NO CORE MODIFICATION / NO NEW ATOMS / NO TRADING LOGIC CHANGE
```

**المحسوم الآن:**
1. **الجدار معروف ومقيس:** `pickle / isolated copy = 33.9%` — الاختناق الأول.
2. المشكلة ليست «نحتاج CPU أكثر» بل **Event Transport Model** هو ما يُعاد تصميمه.

6. **النسخ المتكرر هدف معماري مباشر** — نموذج ملكية/مرجع/ذاكرة يمنع نسخ الحدث عشرات المرات بلا ضرورة.

## ٠-و · قراءة القياس الثاني + القرار المعماري (المالك — ٢٦-٠٨)

**القياس الثاني (16:03) يغيّر الصورة الرقمية، لا القرار المعماري.**

| الحمل | النسبة | الحكم |
|---|---|---|
| **نسخ الحمولة** | **40.6%** | **الاختناق رقم 1** |
| التحليل الحقيقي | 16.4% | الشغل المفيد |
| التخزين | 12.0% | اختناق ثانوي مهم |
| الناقل Bus | 11.5% | اختناق معماري مهم |
| بثّ اللوحة | 5.8% | غير مناسب للمسار الحرج |
| Stamp | 2.9% | كلفة سباكة |
| الشبكة | 1.3% | صغيرة |
| قراءة العيارات | 0.6% | لم تعد مشكلة |
| UUID | 0.7% | لم تعد مشكلة |
| idle | 5.2% | مجال، لكن ليس كبيرًا |

**الرقم الرسمي الجديد:** `COPY = 40.6%` — **الجدار الحالي رقم 1**، أكبر من **ضعف** التحليل (16.4%).

**الجزء الأكبر من CPU حاليًا يذهب إلى النقل والتخزين والإخراج والكلفة التشغيلية**، بينما التحليل الحقيقي **16.4%** فقط. (لا نثبّت رقم «سباكة» إجماليًّا — جمعه يعتمد على تعريف الفئات، وفي الجدول `Other` و`Idle`.)

**تحذير المقارنة:** لا تُقارَن نسب القياسين كأنها نفس التجربة (الحمل/العيّنة يتغيّران). الثابت المهم: **Copy بقي الاختناق الأول** (33.9% → 40.6%).

**الخطأ الذي يمنعه هذا القياس** — لا نزيد عمّال تحليل فوق نسخ+ناقل مركزيين:
```text
             ┌── Cooker A
TICK → COPY →├── Cooker B      ← COPY يصير عنق الزجاجة قبل الطبّاخين
             ├── Cooker C
             └── Cooker D
```

**الاتجاه الذي تبحثه الورقة الآن** — بشرط أساسي: **لا Copy مركزي قبل توزيع العمل**:
```text
TICK → INGESTION → ROUTING → [OWNER A | OWNER B | OWNER C] → COMPUTE → CONTROL/OUTPUT
```

**السؤال الجذري للدراسة:**
> **هل نستطيع نقل «ملكية الحدث» بدل «نسخه»؟**

بدل `Tick → 40 نسخة → 40 مستهلك`، نبحث:
```text
Tick → Payload واحد آمن للقراءة → توزيع الملكية/المرجع → Workers
```
مع الحفاظ على **العزل + الترتيب + عدم فساد الحالة**. إذا نجح هذا = **ضربنا الجذر**.

**الخلاصة (تقوّي القرار السابق):** لا نحل QUANT_NQ بإضافة Threads/Cookers فوق **ناقل ونسخ مركزيين**. نحتاج دراسة **إعادة تصميم Event Transport + Ownership + Memory + Worker Architecture**. الـ6 أنوية تُستخدم **بعد** تحديد الملكية، لا قبلها.

- بالمسار الساخن: `parameter_registry._lock` (كل قراءة عيار) · `live_analysis._schema_lock`.
- خارجه: `metrics._lock` · `hot_reload._scan_lock` (كل 5ث).
- **التسلسل الحقيقي = الحلقة الواحدة + الـGIL** (لا قفل mutex متنازَع عليه اليوم لأن الخيط واحد) — **لكن هذه الأقفال تصبح نقاط تنازع فور تعدّد العمّال**، فهي قيد تصميم على أي توزيع.

**٤) التوقيت لكل مرحلة (queue_wait / compute_time لكل خطوة §٩):** **غير متاح** بلا تركيب أدوات قياس داخل الكود (instrumentation) = تعديل كود، ممنوع الآن. المتاح بلا لمس: توزيع CPU لكل مرحلة (§٠-ب/§٠-و) + أعماق طوابير صناديق البريد. القياس الزمني الدقيق يُبنى ضمن ورقة التنفيذ لاحقًا.

**خلاصة رقم ١:** الشلّال كثيف (128 نوع، 32+/ث مسلَّمًا)، والحمل مؤكَّد **آلة لا سوق** (96% عند 0.2 تكّة/ث)، والأقفال الحاليّة تفترض خيطًا واحدًا وتتعارض مع التوزيع — والتوقيت الدقيق لكل مرحلة يحتاج instrumentation في ورقة التنفيذ.

---

## ٠-ح · الخطوة التالية المعتمدة — Event Ownership & Transport Study (المالك ٢٦-٠٨)

**لا تُكتب ورقة تنفيذ للـ6 Cookers الآن.** الخطوة الصحيحة التالية = **دراسة واحدة محدّدة** تجيب فقط على:
```text
- هل يمكن أن تصبح الحمولة Payload واحدة بدل Copy لكل Subscriber؟
- ومن يملكها؟
- كيف تصل للـWorker؟
- كيف نحافظ على ترتيب Account × Symbol؟
- كيف نمنع Worker من تخريب حالة Worker آخر؟
- كيف يتم Fan-out بدون Central Copy Bottleneck؟
- كيف يعمل Hot Path بدون Persistence/Dashboard؟
- وكيف نتعامل مع overload؟
```
إذا انحلّ هذا على الورق → عندها **فقط** ننتقل لتصميم الـWorkers وتوزيع الـ6 Cores. ولا يُعكَس ترتيب الأولويات (§٠-ب) بإضافة Workers قبل إزالة الاختناق المركزي في النقل.

**→ أُجيبت هذه الدراسة في ورقة `١٨-A · Event Ownership Architecture` (TARGET DESIGN — مقترح للاعتماد، بانتظار كلمة المالك). وورقة التنفيذ `١٨-B` لا تُكتب قبل الاعتماد.**

## ١ · السؤال الذي يجب أن تجيب عنه الورقة

كيف نجعل QUANT_NQ قادرًا على معالجة `Ticks + Events + Accounts + Symbols + Atoms` بالتوازي، دون أن يتحول مسار مركزي واحد إلى عنق زجاجة؟
**الهدف ليس** جعل النظام الحالي أسرع قليلًا. **الهدف:** إزالة الاختناق المعماري الذي يمنع التوسع.

## ٢ · المشكلة

يجب فحص المعمارية الحالية باعتبار احتمال وجود مسار مركزي يتحمل:
```text
استقبال الحدث → توزيع الحدث → عزل المستهلكين → نسخ البيانات → تشغيل العمل
```
إذا كان مركزيًا، فإن زيادة `Events × Subscribers × Accounts × Symbols × Compute` تزيد الضغط على **نفس النقطة**.

## ٣ · مبدأ التصميم

لا يكون: `كل شيء ← طابور واحد ← عامل واحد`. ولا يكون الحل: `نفس الطابور + نسخ أكثر + Workers أكثر`.
بل يجب فصل: `INGESTION · ROUTING · OWNERSHIP · COMPUTE · PERSISTENCE · CONTROL` بحيث لا تعتمد كل المنظومة على مسار تنفيذ واحد.

## ٤ · وحدة العزل الأساسية

الوحدة المرشحة للدراسة: `ACCOUNT × SYMBOL` (Account A × NQ · A × ES · B × NQ …). كل وحدة تمتلك حالة تشغيل واضحة.
**هدف العزل:** تعطل أو بطء وحدة واحدة لا يحوّل النظام كله إلى طابور انتظار.

## ٥ · مفهوم الطبّاخ (Cooker)

الـCooker وحدة تنفيذ مستقلة تحمل مجموعة محددة من العمل. المطلوب دراسة `1 · 2 · 4 · 6` طبّاخين — وليس افتراض أن `6 Cores = 6 Cookers` قبل القياس.

## ٦ · المعمارية المستهدفة — مرشّح أولي (رسم بحثي فقط، غير معتمد)
```text
                 MARKET / FEEDS
                       │
                       ▼
                ┌─────────────┐
                │ INGESTION   │
                └──────┬──────┘
                       ▼
                ┌─────────────┐
                │ EVENT ROUTER│
                └──────┬──────┘
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       COOKER A     COOKER B     COOKER C
          ▼            ▼            ▼
       OWNED WORK   OWNED WORK   OWNED WORK
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       COOKER D     COOKER E     COOKER F
          └────────────┼────────────┘
                       ▼
                 CONTROL / OUTPUT
```

## ٧ · كيف توزَّع الوحدات؟ (نماذج تُقارَن بالقياس)

- **A — حسب الحساب:** Worker → Account.
- **B — حسب الرمز:** Worker → Symbol.
- **C — Account × Symbol:** ملكية Worker = (حساب × رمز).
- **D — Dynamic Scheduler:** التوزيع يتغير حسب الحمل.

لا يُختار النموذج قبل القياس.

## ٨ · قاعدة التوازن

لا نريد `Cooker1=95% · Cooker2=10% · …` بينما هناك عمل ينتظر. المطلوب دراسة: `load balancing · work stealing · dynamic assignment · partitioning` — مع الحفاظ على ترتيب الأحداث حيث يكون مطلوبًا.

## ٩ · مسار التكة الكامل

`SOURCE → RECEIVE → VALIDATE → ROUTE → QUEUE → WORKER → ATOM → RESULT → PUBLISH`. لكل مرحلة يُسجَّل: `timestamp_in · timestamp_out · queue_wait · compute_time` — حتى نعرف أين يذهب الزمن.

## ١٠ · لا فقد صامت (مصحّح ٢٦-٠٨ — لا «صفر إسقاط مطلق»)

الهدف ليس `Dropped = 0` مطلقًا (قد يكون قاسيًا معماريًّا)، بل **لا فقد صامت للبيانات**. عند `OVERLOAD` يجب أن يعرف النظام ماذا يفعل، **ويسجّل الحدث**، ولا يرمي بلا علمنا. الأحداث غير الحرجة قد تكون لها سياسة إسقاط مختلفة مستقبلًا — **يحدّدها العقد، لا تُحسَم هنا مسبقًا**.

## ١١ · الترتيب

بعض الأحداث تتطلب `A B C` بنفس الترتيب. لا يُسمح بتوازٍ عشوائي ينتج `A C B` حيث يتطلب العقد ترتيبًا. يُحدَّد: ما الذي يحتاج ترتيبًا؟ وما الذي يمكن أن يتوازى؟

## ١٢ · الذاكرة

يجب منع `Event → Copy → Copy → Copy …` عشرات المرات لكل تكة. تُدرَس: `immutable payload · shared read-only data · reference passing · object pooling · ring buffers · bounded queues` بحسب سلامة النظام.

## ١٣ · Hot Path

المسار الحرج للتكة أقصر ما يمكن. تُخرَج من `TICK → DECISION` العملياتُ غير الضرورية: `heavy persistence · logging الثقيل · analytics غير الفورية · reports · historical aggregation`.

## ١٤ · Cold Path

غير الحسّاس للزمن ينتقل لمسار منفصل: `HOT: Tick → Analysis → Decision` · `COLD: Logging → Persistence → Reports → Historical`. لمنع الأعمال الثقيلة من تعطيل التكة.

## ١٥ · قاعدة الأقفال

البحث عن: `global locks · shared mutable state · synchronized bottlenecks · database locks`. أي قفل عالمي في المسار الساخن = مرشّح مباشر للاختناق.

## ١٦ · قاعدة قاعدة البيانات

لا تصبح: `Tick → DB write → wait → next work` إن لم يكن ضروريًا. تُدرَس: `buffer · batch · async persistence · dedicated writer` للمسار البارد.

## ١٧ · استخدام المعالج

`6 physical / 12 logical` لا يعني استخدام 12 Thread لكل شيء. يُحدَّد بالقياس: `CPU ownership · worker count · thread affinity · I/O threads · compute threads · control thread`.

## ١٨ · GPU

ليس جزءًا إلزاميًّا. `CPU = Primary` · `GPU = Optional accelerator` يُستخدم فقط إن أثبت القياس فائدته لمهمة محددة — لا لمجرد أن الحمل ارتفع.

## ١٩ · Backpressure

`INPUT RATE > PROCESSING RATE` يجب ألا ينهار النظام بصمت. يُعرَّف: `queue limit · overload state · backpressure · recovery · alert`.

## ٢٠ · عزل العامل البطيء

إذا صارت `Account A × NQ` ثقيلة جدًّا، لا توقف `Account B × NQ · A × ES · C × GC`. من أهم اختبارات المعمارية الجديدة.

## ٢١ · التوسع

لا نقيس `1000 atoms` فقط، بل `Atoms × Events/sec × Accounts × Symbols × Compute weight`. نموذج الاختبار `100 → 200 → 300 → 500 → 750 → 1000` ثم زيادة الحسابات والرموز.

## ٢٢ · الاختبار الأساسي (Load Test يمثّل الحمل الحقيقي)

مدخلات: `Ticks/sec + Accounts + Symbols + Atoms/account + Subscribers + Payload size`. تسجيل: `p50 · p95 · p99 · max latency · queue depth · CPU · RAM · event loss · worker imbalance`.

## ٢٣ · لا رقم نجاح مسبق

لا نكتب `1000 = ناجح` قبل القياس. نحدد بعده: `capacity · safe capacity · degradation point · failure point`.

## ٢٤ · اختبار الانهيار

`100 → 200 → 300 → 500 → 750 → 1000 → 1500 → 2000`. عند التدهور نسجّل `first degradation point`؛ عند الانهيار `failure point`. الهدف معرفة **منحنى القدرة**، لا مجرد النجاح عند 1000.

## ٢٥ · معيار «لا تأخير» (تعريف هندسي)

ليس «صفر تأخير»، بل: زمن معالجة محدود قابل للقياس لا ينمو بلا حدود ضمن السعة المصمَّمة. أي: `Queue لا تنمو بلا نهاية · Latency لا تنفجر · Throughput يبقى مستقرًا`.

## ٢٦ · الفشل المقبول

سقوط `Account × Symbol` يكون `LOCAL` لا `SYSTEM-WIDE`.

## ٢٧ · إعادة التشغيل

تُدرَس: `worker crash · worker restart · queue recovery · state recovery · event recovery` — فشل عامل واحد لا يعيد تشغيل النظام كله.

## ٢٨ · المراقبة

اللوحة المستقبلية تعرض: `Workers · CPU/Core · Queue depth · Events/sec · Ticks/sec · Latency · Dropped events · Worker load · Memory · Slow workers · Overload state`.

## ٢٩ · ما لا يتغير

هذه المعمارية **لا تغيّر منطق التداول**: لا تغيير في `Analysis · Strategy · Decision · Risk · R_B · Risk Dial · Execution Rules · Broker Rules`. الهدف: **طريقة تشغيل الموجود، لا تغيير ما يقرّره الموجود.**

## ٣٠ · ممنوع الترقيع

ليست حلًّا معماريًّا: `زيادة queue · زيادة timeout · زيادة batch فقط · زيادة thread فقط · إخفاء latency · إسقاط الأحداث · تقليل logging فقط · تقليل عدد الذرات · رفع الجهاز الحمل دون تغيير المعمارية`. إن أُزيلت المشكلة بهذه وحدها فهي **ليست إزالة جذرية**.

## ٣١ · CURRENT ≠ TARGET

كل عنصر يُصنَّف `CURRENT · TARGET · UNKNOWN`. لا يُحوَّل `TARGET` إلى حقيقة تشغيلية دون اختبار.

## ٣٢ · خطة الدراسة

`المرحلة 1` رسم الواقع (Tick/Event/Queue/Copy/Lock/DB/Worker path) · `2` قياس (latency/throughput/CPU/memory/queue/copies) · `3` تحديد الجدار (أول اختناق حقيقي) · `4` تصميم ومقارنة نماذج (central/partitioned/account/symbol/account×symbol/dynamic) · `5` اختيار بالقياس · `6` اختبار حمل `100→200→500→1000+` · `7` اعتماد بعد النجاح فقط.

## ٣٣ · معيار النجاح المعماري

`No central compute bottleneck · No unbounded queue growth · No silent event loss · No global serialization · Bounded latency · Stable memory · Balanced CPU · Local failure isolation · Recoverability · Scalable throughput`.

## ٣٤ · السؤال النهائي (يُجاب بالأرقام قبل اعتماد أي تصميم)

كم تكة/ثانية؟ كم حسابًا؟ كم رمزًا؟ كم ذرة؟ ما p99 latency؟ متى يبدأ التدهور؟ أين أول اختناق؟ ماذا عند 1000؟ ماذا عند 2000؟

## ٣٥ · الحالة
```text
ARCHITECTURE STUDY → OPEN → NO IMPLEMENTATION → NO CORE MODIFICATION
→ NO NEW ATOMS → NO TRADING LOGIC CHANGE
```
الورقة لا تقول إن «٦ طبّاخين» هو الحل النهائي. تقول: سنصمّم نظام تشغيل متعدّد الطبّاخين ونثبت بالقياس كيف نستخدم الـ6 أنوية وأين نضع كل نوع من العمل، بحيث لا يعود النظام قائمًا على طبّاخ مركزي واحد. **الهدف النهائي: 1000 ذرة ليست سقف التصميم، بل نقطة اختبار ضمن معمارية قابلة للتوسع.**
